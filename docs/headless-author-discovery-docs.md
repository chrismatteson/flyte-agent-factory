# Headless author: docs research (Claude Code `-p` stream-json vs Agent SDK)

Read-only research, fetched 2026-11-18. Every claim has a URL and a short quote. Items marked UNVERIFIED could not be
confirmed from a primary page. Primary sources: code.claude.com/docs, support.claude.com, anthropic.com/legal, and the
raw source of github.com/anthropics/claude-agent-sdk-python (main) and github.com/anthropics/claude-code CHANGELOG.

## 1. Auth: CLAUDE_CODE_OAUTH_TOKEN, `setup-token`, subscription use

**Verdict.** The token is documented for headless/CI use and works with `claude -p` and the Agent SDK (which spawns the
CLI). Anthropic's published policy line is about *third-party developers offering claude.ai login or routing other
people's usage through plan credentials*. An owner running their own deployment with their own token for their own work
is the "ordinary, individual usage" case. One term needs a conscious decision (Consumer Terms "automated means", see 1.5).

### 1.1 Token is documented for CI/scripts
- https://code.claude.com/docs/en/authentication (Authentication precedence, item 5): "`CLAUDE_CODE_OAUTH_TOKEN` environment
  variable. A long-lived OAuth token generated by `claude setup-token`. Use this for CI pipelines and scripts where browser login isn't available."
- Same page, "Generate a long-lived token": "For CI pipelines, scripts, or other environments where interactive browser login
  isn't available, generate a one-year OAuth token with `claude setup-token`"; "It does not save the token anywhere".
- Same page: "This token authenticates with your Claude subscription and requires a Pro, Max, Ultra, Team, or Enterprise plan.
  It can only make model requests, so it can't establish Remote Control sessions or fetch claude.ai connectors. MCP servers you configure locally still work."
- Gotcha, same page: "Bare mode does not read `CLAUDE_CODE_OAUTH_TOKEN`. If your script passes `--bare`, authenticate with
  `ANTHROPIC_API_KEY` or an `apiKeyHelper` instead." Also https://code.claude.com/docs/en/headless : "In bare mode, Claude Code never reads OAuth credentials or the system keychain." => do NOT use `--bare` with the subscription token.
- Gotcha, same page, precedence: `ANTHROPIC_API_KEY` (item 3) and `ANTHROPIC_AUTH_TOKEN` (item 2) outrank the OAuth token;
  "In non-interactive mode (`-p`), the key is always used when present." Make sure the container has neither set.
- Support article: https://support.claude.com/en/articles/11145838-using-claude-code-with-your-pro-or-max-plan : "If you have an
  ANTHROPIC_API_KEY environment variable set ... Claude Code will use this API key ... instead of your Claude subscription".
- Token robustness (changelog, https://github.com/anthropics/claude-code/blob/main/CHANGELOG.md): "Fixed a transient 401
  replacing a long-lived `CLAUDE_CODE_OAUTH_TOKEN` with a stored login's short-lived token, breaking headless sessions until restart"; "Fixed `/usage` hiding limit bars for setup tokens and `CLAUDE_CODE_OAUTH_TOKEN`: it keeps the session and weekly bars and says why the rest are missing".
- Expiry: one year (above). Expired/refused login in `-p` names the fix: changelog "in `claude -p` names `claude auth login` and `claude setup-token`".

### 1.2 `claude -p` and the Agent SDK with a subscription: what the docs say
- https://support.claude.com/en/articles/17154008 (Monthly API credits): "When you're signed in with your Claude plan instead,
  `claude -p` and Agent SDK usage still draw from your plan's usage limits and don't use your API credits." (Credits apply only
  when using an API key from a linked Console org.) Same text appears in https://support.claude.com/en/articles/15036540-use-the-claude-agent-sdk-with-your-claude-plan : "when you're signed in with your Claude plan, the Claude Agent SDK and `claude -p` still draw from your subscription limits."
- https://code.claude.com/docs/en/legal-and-compliance : "Advertised usage limits for Pro, Max, and Ultra plans assume
  ordinary, individual usage of Claude Code and the Agent SDK."
- Python SDK bundles and spawns the CLI, so auth is the CLI's: https://github.com/anthropics/claude-agent-sdk-python (README) "The Claude Code CLI is automatically bundled with the package". Source `subprocess_cli.py` sets `"CLAUDE_CODE_ENTRYPOINT": "sdk-py"` and builds `[cli_path, "--output-format", "stream-json", "--verbose", ..., "--input-format", "stream-json"]`, i.e. the SDK is literally option (A) with a control-protocol client on top. Option (B) therefore has the same auth/billing behaviour as (A).
- https://code.claude.com/docs/en/authentication notes `apiKeyHelper`, `ANTHROPIC_API_KEY`, `ANTHROPIC_AUTH_TOKEN` "apply to the CLI and the surfaces that wrap it, including ... the Agent SDK"; Agent SDK logins verify `forceLoginOrgUUID` for claude.ai account logins (i.e. claude.ai login is a supported SDK path).
- No page states "the Agent SDK requires API keys". The Agent SDK quickstart does steer toward API keys (see 1.3).

### 1.3 Exact third-party language (the restriction to understand)
- https://code.claude.com/docs/en/agent-sdk/overview (note): "Unless previously approved, Anthropic does not allow third party
  developers to offer claude.ai login or rate limits for their products, including agents built on the Claude Agent SDK. Use the API key authentication methods described in the Quickstart instead."
- https://code.claude.com/docs/en/legal-and-compliance, "Authentication and credential use": "**OAuth authentication** is intended
  exclusively for purchasers of Claude Free, Pro, Max, Ultra, Team, and Enterprise subscription plans and is designed to support ordinary use of Claude Code and other native Anthropic applications."
- Same: "**Developers** building products or services that interact with Claude's capabilities, including those using the Agent SDK,
  should use API key authentication ... Anthropic does not permit third-party developers to offer Claude.ai login into their own applications, or to route requests through Free, Pro, Max, or Ultra plan credentials on behalf of their users. Moreover, developers may not collect, store, or intermediate Claude.ai credentials or session tokens — sign-in to a Claude account must complete through Anthropic's own flow."
- Same, hosted-platform carve-out: "Nor does it prevent an end user from signing in to the unmodified Claude Code binary with their own Claude
  subscription, including where a platform hosts Claude Code". And: "The Claude Code binary must not be modified" and "Customers may not pay for, resell, or intermediate Claude usage on their end users' behalf. Each end user must authenticate with their own Anthropic API key, Claude subscription plan credentials, or 3P inference provider credential".
- Enforcement: "Anthropic reserves the right to take measures to enforce these restrictions and may do so without prior notice."

### 1.4 Product-for-others vs personal automation (our reading, not a doc quote)
- Product for others (prohibited with plan credentials): offering claude.ai login in our app, routing *other users'* requests through one
  subscription, collecting/storing other people's tokens. Their remedy: API key / Console / cloud provider.
- Owner-installed, owner's own token, own infra, own work, unmodified binary: matches "ordinary, individual usage" and the "end user signs in
  to the unmodified Claude Code binary with their own Claude subscription" language. Design constraints that keep us on the right side:
  (a) token is the owner's, supplied by the owner, never by us/our service; (b) we never store or relay tokens centrally; (c) no shared token across
  different humans; (d) do not modify/wrap the binary's auth; (e) do not describe the product as "Claude Code" (branding rules below).
- Branding for SDK-based products, https://code.claude.com/docs/en/agent-sdk/overview : Not permitted: "'Claude Code' or 'Claude Code Agent'".
- Residual risk to flag to the owner: the docs are written around interactive/ordinary use; heavy 24/7 automation draws on the same
  5-hour/weekly windows ("These limits are shared across Claude and Claude Code", support article 11145838).

### 1.5 Consumer Terms (applies to Pro/Max)
- https://www.anthropic.com/legal/consumer-terms prohibits: "Except when you are accessing our Services via an Anthropic API Key or where we otherwise explicitly
  permit it, to access the Services through automated or non-human means, whether through a bot, script, or otherwise." Anthropic's own docs explicitly
  permit `claude -p`/Agent SDK/setup-token usage with plan credentials (1.1, 1.2), which is the "otherwise explicitly permit" path. Also: "You may not share your Account login
  information, Anthropic API key, or Account credentials with anyone else."
- NOTE: a third-party summary claimed a "monthly Agent SDK credit from June 15" separate from plan limits; the primary support pages above say plan-signed-in
  `-p`/SDK usage draws from plan limits and does not use API credits. Treat the blog claim as UNVERIFIED/outdated.

## 2. stream-json input, multi-turn, queueing, control protocol

- Flag: https://code.claude.com/docs/en/cli-reference : "`--input-format` Specify input format for print mode (options: `text`, `stream-json`)";
  example `claude -p --input-format stream-json --output-format stream-json --verbose`. Note `--verbose` is required with stream-json output (headless page examples).
- The CLI docs do NOT publish the stdin JSON schema. Ground truth is the SDK source
  (https://github.com/anthropics/claude-agent-sdk-python `client.py`), which writes one JSON object per line:
  `{"type": "user", "message": {"role": "user", "content": prompt}, "parent_tool_use_id": None, "session_id": "default"}`.
  `content` may be a string or a list of content blocks (docs example with image: https://code.claude.com/docs/en/agent-sdk/streaming-vs-single-mode, "content": [{"type":"text",...},{"type":"image","source":{"type":"base64",...}}]).
  TS `SDKUserMessage` additionally has `priority` ("normal"/"high"/"now" per changelog) and `uuid`: "To choose when Claude reads a message you push during a response, set the message's `priority` field." (same page).
- Multi-turn in one process: yes. https://code.claude.com/docs/en/agent-sdk/streaming-vs-single-mode : "Streaming input keeps an Agent SDK session open so your
  application can send it more than one message while it runs." Python: "open a `ClaudeSDKClient` and pass each message to `client.query()`". Process lifetime: with `-p` + stream-json the process stays up while stdin is open; headless page "After Claude finishes its turn and stdin has closed, a `claude -p` run can stay open to wait for background work".
- Sending while a turn runs: allowed and queued. Same page: "A message you send during tool calls reaches Claude after those tool calls finish.
  Claude then answers it and your earlier message in one response. If the turn ends first, Claude starts a new turn for it." Interrupt: "When you call `interrupt()` during a response, that response ends with an `error_during_execution` result. Messages you sent before the interrupt that Claude hadn't read yet still reach Claude once the interrupted response ends." Idle-turn correlation: TS result carries `user_message_uuids` (same page) and `--replay-user-messages` "Re-emit user messages from stdin back on stdout for acknowledgment" (CLI reference).
- Control protocol (not documented in prose; verified from Python SDK `_internal/query.py`):
  - SDK->CLI request envelope: `{"type": "control_request", "request_id": ..., "request": {"subtype": ...}}`; reply: `{"type": "control_response", "response": {"subtype": "success", "request_id": ..., "response": {...}}}` (or `"subtype": "error"`).
  - Request subtypes sent by SDK: `initialize` (hooks, agents, ...), `interrupt`, `set_permission_mode` (`"mode": mode`), `set_model`, `mcp_status`, `get_context_usage`.
  - CLI->SDK requests handled by SDK: `can_use_tool` (fields `tool_name`, `input`, `permission_suggestions`, `tool_use_id`, `agent_id`, `blocked_path`, ...) answered with `{"behavior":"allow","updatedInput":...}` or `{"behavior":"deny","message":...,"interrupt":bool}`; `hook_callback` (`callback_id`); MCP message passthrough; plus `control_cancel_request` from the CLI.
  - `can_use_tool` is wired when the SDK has a callback; in the SDK source the CLI flag `--permission-prompt-tool` is only added for a named MCP tool (`permission_prompt_tool_name`), and the string `stdio` is NOT found in `subprocess_cli.py`/`query.py` (UNVERIFIED how/whether the CLI is told "stdio"; for a hand-rolled (A) client, read the SDK's `subprocess_cli.py` around lines 575-590 and replicate; for (B) it is handled for you).
  - Interrupt receipts: https://code.claude.com/docs/en/headless : the `system/init` event carries optional `capabilities` strings "such as `interrupt_receipt_v1` or `interrupt_cancel_queued_v1`. Check it to feature-detect instead of comparing version strings".
- Permission prompts under plain `-p`: https://code.claude.com/docs/en/headless : "In a Manual mode `claude -p` run, a call that needs approval is denied unless something approves it, such as a `PermissionRequest` hook or a `--permission-prompt-tool`." and "Without the flag ... your run waits for that host to answer each permission request" (re `--permission-prompts none`, needs v2.1.259+).
- Mid-session mode change: https://code.claude.com/docs/en/agent-sdk/streaming-vs-single-mode : "switch the model or permission mode while the session runs" (streaming input only).

## 3. Output events (stream-json)

- Event kinds named on https://code.claude.com/docs/en/headless : `system/init` ("reports session metadata including the model, tools, MCP servers, and loaded
  plugins. It is the first event in the stream unless startup events precede it"), `system/api_retry`, `system/plugin_install`, `assistant`/`user` ("Messages from subagents ... appear in the stream as `assistant` and `user` messages. Their `parent_tool_use_id` field says which run each one belongs to"), `stream_event`, `permission_denied` system messages, final `result`.
- `session_id` is in init and in every result: https://code.claude.com/docs/en/agent-sdk/sessions : "Read it from the `session_id` field on the result message ... which is present on every result regardless of success or error"; "In TypeScript the ID is also available earlier as a direct field on the init `SystemMessage`; in Python it's nested inside `SystemMessage.data`."
- `result` fields (Python `ResultMessage`, https://code.claude.com/docs/en/agent-sdk/python): `subtype` ("success", "error_during_execution", "error_max_turns", "error_max_budget_usd"), `duration_ms`, `duration_api_ms`, `is_error`, `num_turns`, `session_id`, `stop_reason`, `total_cost_usd`, `usage`, `result`, `model_usage`, `terminal_reason`, `uuid`, plus `permission_denials`, `structured_output`. Headless page: "The last line of the stream is a `result` message with the final response text, cost, and session metadata"; "`total_cost_usd` ... Both figures are client-side estimates and can differ from your actual bill" and with `--resume` "the run reports the conversation's whole total". With a subscription token the cost is an estimate only; do not treat it as spend.
  (CAUTION: a fetch of the TS reference page returned a different subtype list ("end","interrupt",...); that summary is inconsistent with the sessions docs and Python source, ignore it.)
- Usage-limit event: `rate_limit_event`. Python source `types.py`: `RateLimitEvent{rate_limit_info, uuid, session_id}`, `RateLimitInfo{status: "allowed"|"allowed_warning"|"rejected", resets_at: unix ts, rate_limit_type: "five_hour"|"seven_day"|"seven_day_opus"|"seven_day_sonnet"|"overage", utilization: 0.0-1.0, overage_status, overage_resets_at, overage_disabled_reason, raw}`. Docstring: "The CLI emits this whenever the rate limit status transitions ... Use this to warn users before they hit a hard limit, or to gracefully back off when `status == "rejected"`." (https://github.com/anthropics/claude-agent-sdk-python/blob/main/src/claude_agent_sdk/types.py). Python CHANGELOG: "Unrecognized CLI message types (e.g., `rate_limit_event`) would crash the session ... Unknown message types are now silently skipped". Claude Code changelog: "Improved headless `rate_limit_event` usage-limit warnings to say whether the account has extra usage turned on". `resets_at` is a Unix timestamp (units: seconds vs ms UNVERIFIED; check a live event).
- Hitting the cap also surfaces as an assistant message error `rate_limit` (`AssistantMessageError` literal in `types.py`) and `api_retry.error` category `rate_limit`.
- `system/api_retry` fields (headless page table): `attempt`, `max_retries`, `retry_delay_ms`, `error_status`, `error` (`authentication_failed`, `oauth_org_not_allowed`, `account_on_hold`, `billing_error`, `rate_limit`, `overloaded`, `invalid_request`, `model_not_found`, `server_error`, `max_output_tokens`, `cloud_credential_error`, `unknown`), `uuid`, `session_id`. Auth failure is therefore detectable as `error == "authentication_failed"`.
- `stream_event` with `--include-partial-messages`: CLI reference "Include partial streaming events in output. Requires `--print` and `--output-format stream-json`"; shape `{"type":"stream_event","event":{"delta":{"type":"text_delta","text":...}}}` (headless page jq example `select(.type == "stream_event" and .event.delta.type? == "text_delta")`). Python `StreamEvent{uuid, session_id, event, parent_tool_use_id}`.
- Hook events: CLI reference `--include-hook-events` "Include hook lifecycle events in the output stream. `SessionStart` and `Setup` hook events are always included ... Requires `--output-format stream-json`"; events `hook_started`, `hook_progress`, `hook_response`.
- Other system subtypes: `compact_boundary`, `status`, task events (`task_notification`/`task_updated` statuses exist in `types.py`) are present in the SDK message union but I could not fetch their field tables from a primary page (UNVERIFIED fields). Also a warning event when "the working directory ... is deleted" (headless page: "Claude Code emits a warning message in `stream-json` output").
- Exit/signals: headless page "If you stop a `claude -p` run with SIGTERM ... exits with code 143. Claude Code leaves the turn that was in progress unfinished and records no result for it. To end the turn instead, send SIGINT, or call the Agent SDK's `interrupt()`".
- Slow consumer: "If your consumer reads the stream slowly, Claude Code waits for the queued output to drain before exiting ... capped at 30 seconds."

## 4. Resume in `-p` mode

- CLI reference: "`--resume`, `-r` Resume a specific session by ID or name"; "`--continue`, `-c` Load the most recent conversation in the current directory ... `claude -p --continue` includes `-p`, SDK, and `/loop` sessions" (plain `--continue` skips -p/SDK sessions); "`--session-id` Use a specific session ID for the conversation (must be a valid UUID)"; "`--fork-session` When resuming, create a new session ID instead of reusing the original (use with `--resume` or `--continue`)"; `--resume` also accepts "the absolute path to a session's `.jsonl` transcript file".
- Headless page: `claude -p "Continue that review" --resume "$session_id"`; "Claude Code finds the session by its ID in any project on this machine".
- Persistence: sessions are written to `~/.claude/projects/<encoded-cwd>/*.jsonl` (or `$CLAUDE_CONFIG_DIR/projects/`), https://code.claude.com/docs/en/agent-sdk/sessions ; "Same machine only: the session file still needs to exist on the current machine." => a pod restart needs `~/.claude` (or `CLAUDE_CONFIG_DIR`) on persisted storage, or a `SessionStore` adapter (same page). `--no-session-persistence` disables it ("Print mode only").
- Interrupted turn on resume: headless page "set `CLAUDE_CODE_RESUME_INTERRUPTED_TURN=1`" to continue an interrupted turn.
- Python SDK: `ClaudeAgentOptions(resume=..., continue_conversation=..., fork_session=..., session_id=...)`; source passes `--resume=<id>`, `--session-id=<id>`.
- Cost totals accumulate across resumes (headless page, above).

## 5. Hooks, settings, permission modes, sub-agents in `-p` vs interactive

- Settings/hooks/CLAUDE.md/skills/MCP load as interactive unless `--bare`: headless page "Without it, `claude -p` discovers and loads them as an interactive session would, including anything configured in the working directory or `~/.claude`". `--bare` is not usable with the subscription token (section 1.1).
- Hooks run in `-p` and SDK (https://code.claude.com/docs/en/agent-sdk/overview capabilities table: Hooks, Subagents, MCP, Permissions, Sessions; "Skills, commands, and memory ... Load automatically from your project's `.claude/` and from `~/.claude/`, same as Claude Code"). `PermissionRequest` hook can approve in -p (headless page above). Python SDK also supports in-process hook callbacks via the `hook_callback` control request (section 2). `setting_sources` option / `--setting-sources user,project,local` restricts loading.
- Permission modes (CLI reference `--permission-mode`): "Accepts `default`, `acceptEdits`, `plan`, `auto`, `dontAsk`, `bypassPermissions`, or `manual` as an alias for `default`". `--dangerously-skip-permissions` is "Equivalent to `--permission-mode bypassPermissions`". Default in -p: "With Claude Code v2.1.302 or later, `claude -p` runs start in Manual mode when nothing sets a permission mode"; in Manual mode needing-approval calls "are denied unless something approves it". `dontAsk`: "denies every call that would otherwise prompt". `acceptEdits`: writes files and "auto-approves common filesystem commands such as `mkdir`, `touch`, `mv`, and `cp`"; other shell/network need `--allowedTools` or allow rules. https://code.claude.com/docs/en/headless
- Running as root with bypass: UNVERIFIED here; check `permission-modes` page before using bypassPermissions in a root container.
- `--permission-prompts none` (v2.1.259+): in unattended runs "Anything that would prompt is denied ... and Claude is told that nobody can approve the request and not to retry it"; it also removes `AskUserQuestion`. Denials appear as `permission_denied` system messages and in the result's `permission_denials`.
- Sub-agents: work in -p; their messages stream with `parent_tool_use_id`; default forwards only `tool_use`/`tool_result` blocks, text/thinking only "With `--forward-subagent-text` or `CLAUDE_CODE_FORWARD_SUBAGENT_TEXT`". Background subagents: run stays open "until each one finishes or the 10-minute cap ends the wait" (`CLAUDE_CODE_PRINT_BG_WAIT_CEILING_MS`, `0` = no cap) - applies after stdin closes. https://code.claude.com/docs/en/headless
- Command differences in -p: "Built-in commands that only run in the terminal interface, such as `/login`, aren't available"; user-invoked skills and custom commands work via `/skill-name` in the prompt; `/model sonnet`, `/config key=value`, `/mcp` text summary work. https://code.claude.com/docs/en/headless
- Cost cap: `--max-budget-usd` "(print mode only)", client-side estimate, so not meaningful as a spend guard for subscription use.
- Streaming-mode-only features: `interrupt()` and `set_permission_mode()` "Only available in streaming input mode" (TS reference; matches Python `ClaudeSDKClient`).

## 6. Workspace trust dialog in `-p`

- Skipped. https://code.claude.com/docs/en/headless : "A `-p` session shows no workspace trust dialog and no per-server approval prompt."
- https://code.claude.com/docs/en/permissions : "Claude Code shows the trust dialog in interactive terminal sessions, but not in `claude -p` or SDK sessions."
- Consequences (same page, "What runs before you trust a folder"): project `permissions.allow` rules and `additionalDirectories` in `.claude/settings.json` are "Not used. Claude Code prints a `this workspace has not been trusted` warning to stderr" for an untrusted folder; `.mcp.json` servers are "Connected without asking, approved or not"; project hooks still run ("a `-p` session runs the hooks in a project's `.claude/settings.json` and connects the servers in its `.mcp.json`, even in a folder you've never trusted").
- Fix to make project allow rules apply: "set `projects["<path>"].hasTrustDialogAccepted` to `true` in `~/.claude.json`, where `<path>` is the repository root" (same page). Alternatively put allow rules in user settings or pass `--allowedTools`/`--permission-mode`.
- `.claude/settings.local.json`: "you're in a `-p` or SDK session, which counts as accepted" (same page).

## Recommendation hooks for the design (informal)
- (B) is (A) plus a maintained control-protocol client: same binary, same auth, same billing. Prefer (B) unless a Python SDK limitation bites; use (A) only if the author must stay a dependency-free subprocess and you are ready to implement `control_request`/`control_response`.
- Always: unset `ANTHROPIC_API_KEY`/`ANTHROPIC_AUTH_TOKEN`; do not pass `--bare`; persist `~/.claude`; handle `rate_limit_event` (`status`, `resets_at`) and `api_retry.error == authentication_failed`; use SIGINT/`interrupt()` rather than SIGTERM.
